# 팀 협업 가이드

## 브랜치 전략과 선택 이유
우리 팀은 GitHub Flow를 사용한다.
작업별 브랜치와 PR로 변경 사항을 검토하여 main을 안정적으로 유지한다.
짧은 작업을 자주 병합하여 문제를 일찍 발견하고 협업 기록을 남긴다.

## 브랜치 네이밍
- `main`: 검증된 결과물을 유지하는 기본 브랜치
- `feature/<이름>-<작업>`: 작업 단위 브랜치
- 예: `feature/songha-contributing`
- 새 작업은 최신 main에서 새 브랜치를 만들어 시작한다.
- main에 직접 push하지 않는다.

## 커밋 메시지
형식: `<유형>: <구체적인 변경 내용>`

- feat: 기능 추가
- fix: 오류 수정
- docs: 문서 작성 또는 수정
- refactor: 동작을 유지하는 코드 구조 개선
- chore: 설정 및 기타 관리 작업

좋은 예:
- `docs: 협업 가이드에 브랜치 네이밍 규칙 추가`
- `docs: 승재 소개 문서의 제목 공백 수정`

금지 예:
- `update`
- `fix`
- `wip`
- `edit file`

파일명만 적지 않고 무엇을 바꿨는지 설명한다.

## Issue와 PR
- 작업을 시작하기 전에 Issue를 생성한다.
- PR 본문에 `Closes #이슈번호`를 작성한다.
- PR에는 변경 사항(What), 변경 이유(Why), 검증 방법(How)을 포함한다.
- 모든 feature 브랜치의 변경은 PR로 main에 병합한다.
- 작성자 외 팀원 1명 이상의 승인을 받는다.
- 모든 리뷰 대화를 해결하고 검증을 마친 뒤 병합한다.

## 코드 리뷰
- 본인 PR은 본인이 승인하지 않는다.
- 각 PR에 파일이나 특정 라인을 근거로 한 실질적인 의견을 남긴다.
- 질문, 대안, 위험 요소 또는 개선 방법을 구체적으로 작성한다.
- LGTM 또는 좋아요만으로 리뷰를 끝내지 않는다.
- 작성자는 의견에 답변하고, 수정한 경우 커밋을 알려준다.
- 리뷰어는 반영 결과를 확인한 뒤 승인한다.



## 검증 방법
- Markdown 문서는 미리보기에서 제목과 목록을 확인한다.
- 문서 링크가 올바른 파일을 가리키는지 확인한다.
- 다른 팀원의 내용을 실수로 삭제하지 않았는지 diff를 확인한다.

## 충돌 대응
1. 충돌이 발생하면 PR 작성자를 해결 담당자로 정하고, 같은 파일을 수정한 팀원을 공동 확인자로 지정한다.
2. PR 작성자와 상대 변경 작성자가 두 변경의 의도를 확인하고, 충돌한 브랜치 이름과 파일 경로를 PR 댓글에 기록한다.
3. 필요한 내용을 함께 보존하도록 해결한다.
4. 충돌 마커를 제거하고 최종 파일을 검증한다.
5. 해결 내용을 커밋하고 PR에 공유한다.
6. docs/conflict-resolution.md에 참여자, 상황, 명령, 결과와 배운 점을 기록한다.

## 히스토리 보호
- 공유 브랜치에서는 무리한 히스토리 재작성을 하지 않는다.
- 팀 합의 없이 강제 push나 rebase를 하지 않는다.
- 이미 공유한 커밋의 변경을 취소할 때는 revert를 우선 검토한다.
